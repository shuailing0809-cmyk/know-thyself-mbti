## 2. 产品目标理解

要开发的是一个“对话式 MBTI 测评 Agent”，核心价值不是输出四个字母，而是通过自然语言对话收集真实行为证据，并在证据不足时用高质量追问补足判断依据。

用户体验目标：

- 用户用自然语言开始测评。
- Agent 先欢迎并等待用户确认开始。
- Agent 按固定顺序提出 4 个情境问题：`EI -> SN -> TF -> JP`。
- 每次只问一个问题，必须等待用户回答。
- 用户回答模糊时，按规则自然追问。
- 每个维度最多追问一次。
- 四维完成后输出分层报告。
- 置信度不足时保守表达，不强行定型。
- 报告要具象、清楚、逻辑化，避免星座式泛化和绝对标签。

用户侧不能看到的内容：

- 证据层级代号。
- 报告层级代号。
- 置信度计算细节。
- 状态机、调试日志、维度打分过程等研发术语。

## 3. 核心测评流程

正式流程按资料包中的 `08_对话流程设计.md` 实现：

1. 欢迎层。
2. 等待用户确认开始。
3. 提出 EI 主测题。
4. 等待用户回答。
5. 必要时进行 EI 追问。
6. 提出 SN 主测题。
7. 等待用户回答。
8. 必要时进行 SN 追问。
9. 提出 TF 主测题。
10. 等待用户回答。
11. 必要时进行 TF 追问。
12. 提出 JP 主测题。
13. 等待用户回答。
14. 必要时进行 JP 追问。
15. 输出结果报告。
16. 结果后邀请用户反馈。

欢迎语使用资料包中的基准版本，允许轻微润色但不娱乐化：

```text
欢迎来到心灵空间。

我会通过 4 个情境问题帮你更好地了解自己——这不是诊断，只是自我探索，你可以随时退出。

准备好了就开始。
```

## 4. 四维判断规则摘要

### EI：能量来源

真正识别的是用户在常态下恢复能量时，更偏向人和互动，还是更偏向独处和安静。

判断要点：

- E 倾向：主动约人、热闹、社交后更有能量、没人约会觉得少了点什么。
- I 倾向：独处、安静、社交后需要恢复、一个人待着才像充电。
- 不测社交能力，不因工作需要社交就判 E。
- 用户只描述活动时，要追问活动后的能量感受。
- 用户说看状态时，要识别精力状态污染。

主测题：

```text
假设你有一个完整的周末或小长假，没有任何必须做的事，你一般会怎么安排这段时间？能想到平时比较多的情况就行。
```

追问：

```text
这样安排完之后，你通常感觉怎么样？是更放松、更有能量，还是反而有点累、需要一个人静静才能恢复？
```

### SN：信息偏好

真正识别的是用户建立理解时，默认先抓具体步骤与事实，还是先抓框架、结构、逻辑和关联。

判断要点：

- S 倾向：先找教程、步骤、说明书、别人的做法，按顺序来。
- N 倾向：先理解原理、整体框架、底层逻辑，步骤是后续填充。
- 不测聪明程度，不因专业背景或任务类型简单判定。
- 用户只说“先了解整体”但没有第一步行为时，要追问。
- 用户说“看内容”时，要识别任务类型污染。

主测题：

```text
如果要你快速学一个完全陌生的东西，比如一个新软件、一道新菜、一门完全没基础的课，你通常会怎么开始？能举一个你印象比较深的情况。
```

追问：

```text
你当时第一步具体做了什么？是先找教程步骤，还是先找原理？按你大多数时候的习惯来说。
```

### TF：决策权重

真正识别的是当原则、合理性、边界与感受、关系、和谐冲突时，用户默认先顾哪一边。

判断要点：

- T 倾向：更看事情合不合理，直接说明原因，关系归关系，事情归事情。
- F 倾向：更担心对方感受、关系影响，拒绝时难开口或更委婉。
- 不测“理性 vs 感性”的刻板印象。
- 用户说“会纠结”但没说纠结点时，要追问默认权重。
- 用户说“看人/看关系”时，要识别关系类型和权力结构影响。

主测题：

```text
如果有个人找你帮忙，或者请你做一件你觉得不太合理、或者会占用你时间的事，你通常会怎么处理？能举一个你印象比较深的情况。
```

追问：

```text
当时你内心更纠结的是什么？是觉得不符合你的原则或安排，还是更担心拒绝后会让对方不高兴、或者影响你们的关系？按你大多数时候的反应来说。
```

说明：资料包中部分 TF 追问文本出现“高兴/不高心”等明显错字，实现时应修复为“不高兴”，不改变题目含义。

### JP：行动组织

真正识别的是用户面对不确定性和变化时，默认更偏向先定下来、先收拢，还是边做边调、保留弹性。

判断要点：

- J 倾向：提前计划、安排好、没计划不安心、变化时想赶紧重新安排。
- P 倾向：大致方向即可、保留弹性、边走边看、变化带来空间。
- 不测自律或拖延，不因工作要求或截止日期简单判 J。
- 用户只说会计划但没说变化反应时，要追问。
- 用户说“看重要程度”时，要识别任务重要性污染。

主测题：

```text
假设你要去一个从没去过的地方玩两天，或者要操办一件对你来说挺重要的事，你一般会怎么准备和推进？能举一个你印象比较深的情况。
```

追问：

```text
后来如果有临时变化，比如原本订好的地方、时间、方式要调整，你通常会怎么反应？按你大多数时候的情况来说，是会想赶紧重新安排好，还是觉得无所谓、顺着走就行？
```

说明：资料包 CSV 中 JP 追问存在一处乱码，实现时应按 Markdown 文档中的正常版本修复。

## 5. 追问规则

追问的目标是补行为证据，不是引导用户答成某一端。

执行规则：

- 每个维度最多追问一次。
- 只有主回答存在关键证据缺口时才追问。
- 追问后无论回答质量如何，都要对该维度收口。
- 用户拒绝补充时，用温和话术收口并进入下一题。
- 用户只回答“都有/看情况/不一定”时，不能强行推成强倾向。
- 用户回答前后矛盾时，温和指出矛盾并请求澄清；这一类纠偏也要保持一次响应只做一个动作。

典型触发条件：

- EI：只有活动安排，没有能量感受。
- SN：只有偏好表态，没有第一步行为。
- TF：知道会纠结，但没有默认权重。
- JP：只有计划表态，没有变化反应。

特殊处理：

- “看状态/看内容/看关系/看重要程度”进入情境依赖处理。
- 追问后仍只有抽象表态时，分数回到中间附近，报告保守。
- 明显情境依赖时，不给强倾向。

## 6. 评分实现计划

### 6.1 数据输入

第二阶段会把资料复制到 `app/data/`：

- `questions.csv`
- `scoring_rules.yaml`
- `report_templates.md`

实现时会优先使用结构化数据，不把题目硬编码在业务逻辑里。

### 6.2 评分输出结构

每个维度完成后生成一个内部 `DimensionResult`：

- `dimension`: `EI/SN/TF/JP`
- `score`: 1-10
- `direction`: 该维度倾向字母
- `evidence_level`: 证据强度
- `confidence`: 0-1
- `needs_followup`: 是否需要追问
- `followup_used`: 是否已经追问过
- `context_dependency`: 是否存在情境依赖
- `user_visible_reason`: 给报告使用的自然语言判断依据
- `internal_notes`: 仅用于日志和测试，不展示给用户

### 6.3 证据层级

按资料包规则实现：

- L1：自我标签，不能单独作为高置信依据。
- L2：偏好表态，中等证据，需要行为过程支撑。
- L3：行为过程，核心证据。
- L4：稳定性与排他，支持更明确分数。

用户侧不展示 L1/L2/L3/L4，只展示“你的回答里提到的行为依据”。

### 6.4 分数区间

按 `05_评分规则.yaml`：

- 1-4 倾向左端字母。
- 5-6 为中间/平衡。
- 7-10 倾向右端字母。
- 只有 L1/L2：最多给 4-6，置信度不超过中低水平。
- 有 L3：可给 2-8。
- 有稳定排他 L4：才允许接近 1 或 10。
- 追问后仍只有 L1/L2：给 5，低置信度。

维度字母方向按资料包 YAML：

- EI：左端 E，右端 I。
- SN：左端 S，右端 N。
- TF：左端 T，右端 F。
- JP：左端 J，右端 P。

### 6.5 初版自然语言判断方式

最小可运行版本建议采用规则引擎优先：

- 关键词识别。
- 行为动词识别。
- 稳定性词识别，例如“总是/每次/大多数时候/基本上”。
- 排他词识别，例如“必须/受不了/完全不/一定要”。
- 模糊词识别，例如“都有/看情况/不一定/说不准”。
- 情境依赖词识别，例如“看人/看关系/工作和生活不同/看状态/看内容/看重要程度”。

后续可以在规则引擎外增加 LLM 解释层，但第二阶段先保证可测试、可复现。

## 7. 状态管理实现计划

### 7.1 会话状态

内部 `SessionState` 建议包含：

- `session_id`
- `status`: `idle / waiting_confirmation / waiting_answer / waiting_followup / completed / exited`
- `current_dimension`
- `dimension_order`: `EI, SN, TF, JP`
- `asked_questions`
- `answers`
- `dimension_results`
- `followup_counts`
- `created_at`
- `updated_at`

### 7.2 状态持久化

第二阶段本地版本建议使用文件型存储，便于测试和迁移：

- 默认存储在 `storage/sessions.json` 或 SQLite。
- CLI 和 HTTP API 共享同一套状态管理。
- HTTP API 通过 `session_id` 管理单用户会话。
- 微信公众号阶段改用 OpenID 作为稳定用户标识。

### 7.3 状态流转约束

- 未确认开始时，不进入第一题。
- 当前维度未完成时，不进入下一维度。
- 同一维度最多一次追问。
- 四维未完成前，不生成报告。
- completed 后再次输入，提示可重新开始或查看结果。
- 用户退出时，状态设为 exited，不继续提问。

## 8. 报告生成计划

### 8.1 报告层级

按资料包保留三层输出：

- 高清晰度报告：四维倾向较清晰，可以适度展开。
- 中等清晰度报告：有 1-2 个模糊维度或情境依赖，保守表达。
- 低清晰度报告：多个维度模糊，只输出极简参考方向。

内部判定指标：

- 强偏向维度数量。
- 平衡维度数量。
- 情境依赖程度。
- 信息不足维度数量。
- 整体置信度。

用户侧只看到自然语言说明，不看到内部判定公式。

### 8.2 报告内容

所有层级都必须包含：

- 类型结论或参考方向。
- 四维倾向。
- 判断依据。
- 边界声明。

高清晰度报告额外包含：

- 类型说明。
- 典型表现。
- 沟通风格。
- 压力状态。
- 协作建议。
- 可能误判点。

中等清晰度报告：

- 不展开完整人格画像。
- 明确哪些维度较稳定，哪些维度可能切换。
- 给相邻类型提示。

低清晰度报告：

- 不输出完整类型画像。
- 明确说明当前信息不足。
- 把结果定位为探索入口。

### 8.3 相邻类型

按报告模板规则：

- 优先找 5-6 分维度。
- 必要时参考 4 或 7 分维度。
- 只替换最接近平衡的 1-2 个维度字母。
- 说明为什么可能在相邻类型间切换。

### 8.4 知识库缺口

`07_输出报告模板.md` 提到调用 `MBTI_KNOWLEDGE.md`，但资料包未包含该文件。

第二阶段有两种方案需要确认：

- 方案 A：先实现报告框架和四维依据，不写深度 16 型知识库，避免生成通用百科。
- 方案 B：由你补充 `MBTI_KNOWLEDGE.md` 后再接入完整类型说明。
- 方案 C：我基于现有资料起草一个最小 16 型知识库，但需你确认后使用。

我建议先采用方案 A 完成本地可运行 Agent，再补知识库增强 H 层报告。
